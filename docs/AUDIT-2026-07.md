## Executive summary

| Severity | Count |
|---|---|
| Critical | 1 |
| High | 7 |
| Medium | 15 |
| Low | 13 |

**Overall posture.** This is a well-built codebase. The layering is disciplined (routes → services → models, protocols for VectorStore/StorageBackend/Embedder, zero service→route imports), the design-token system is genuinely strong, the tenancy boundary is correct and tested, and the security fundamentals that are *hard* to get right are right: JWT algorithm is pinned on decode, path traversal is blocked at every storage entry point, storage keys are always server-derived, ownership returns 404-not-403, the Unsplash SSRF check is sound, and there is not a single HTML-injection sink in the entire frontend. 153 backend tests and 72 frontend tests pass; ruff, mypy, and ESLint are all clean.

The problems are concentrated in three places: **the perimeter around the app (dev infrastructure, rate limiting, dependency freshness)**, **resource-exhaustion defenses on untrusted file uploads**, and **the gap between "tests pass" and "the build works."**

### Top 6 must-fix

1. **[SEC-01 · Critical]** Mongo and Chroma are published on *all* network interfaces with no authentication. Verified live: I read the `users` collection (emails + bcrypt hashes) over the network. The macOS firewall is off and the host is on a LAN. ChromaDB 1.5.9 additionally carries a pre-auth RCE with **no patched version available**. Two-line fix.
2. **[BUILD-01 · High]** `npm run build` is **broken on `dev`** (9 TypeScript errors). The next milestone is a dev→main release; this blocks it outright. It merged because nothing gates the build.
3. **[SEC-02 · High]** `POST /api/auth/demo-login` issues a full bearer token with **no credentials**, and every AI generation route is deliberately exempt from the demo guard — with no rate limiting anywhere. An anonymous attacker gets unbounded Anthropic/OpenAI spend and an unbounded Mongo write primitive.
4. **[SEC-03 · High]** Uploaded `.docx` templates are rendered as **Jinja2 source** synchronously inside an `async def`, with no timeout. A nested `{% for %}` loop bomb freezes the entire uvicorn worker for every user. Proven.
5. **[SEC-04 · High]** Zip-bomb: only the *compressed* upload size is capped. A crafted 48 KB `.docx` expands to 50 MB (**1,011× amplification**); at the 10 MB cap that is ~11 GB of RAM. Proven.
6. **[SEC-05 · High]** Vulnerable dependencies, several reachable: `python-multipart==0.0.6` (two HIGH DoS advisories — and it parses *every* upload), `python-jose==3.3.0` (CRITICAL algorithm-confusion, fixed in 3.4.0).

### Posture by area

- **Security** — Strong fundamentals, weak perimeter. Every finding below is a *missing outer defense* (rate limits, resource caps, network binding, dependency currency), not a broken inner one.
- **Architecture** — Healthy. No High findings. The debt is horizontal repetition of cross-cutting scaffolding (upload validation ×9, SSE framing ×4, streaming-hook machinery ×4), not structural rot. One fork has already produced a live user-visible bug (ARCH-04).
- **Styling** — Excellent token discipline: all 13 tokens have dark counterparts, z-index is 100% token-driven, zero leaked chrome hex. One real gap (the type scale was never encoded, so ~40 arbitrary values and six different eyebrow trackings leaked in).
- **Accessibility** — Good ARIA hygiene undermined by two real blockers: the SSE token stream sits inside an `aria-live` region (floods screen readers on the app's core flow), and the accent-foreground picker can render the primary CTA at 1.07:1 contrast.
- **Tests** — 225 passing tests with genuinely good tenancy coverage — but **authentication is untested on both sides**, and the frontend has no flow tests at all.
- **Tooling/CI** — **No CI exists.** That is the root cause of BUILD-01 and will be the root cause of the next one.
- **Deployment** — Deferred per `docs/PLAN.md`, and correctly so; the Dockerfile has never been built. One deploy item is a today-risk anyway (DEP-01).

## Security

### SEC-01 · Critical · Unauthenticated Mongo + Chroma exposed to the local network
`docker-compose.yml:7-8,15-16`

`ports: "27017:27017"` and `"8001:8000"` use Docker's short syntax, which binds **`0.0.0.0`**, not loopback. Mongo has no auth configured at all (no `MONGO_INITDB_ROOT_USERNAME`), and Chroma has none either.

**Verified live, not theoretical.** Against the running stack I connected with no credentials and read:

```
UNAUTHENTICATED CONNECTION SUCCEEDED. databases: ['admin', 'brand_content', 'brand_content_test', 'config', 'local']
collections: ['workspaces', 'generations', 'templates', 'users', 'assets']
users readable -> email=demo@folio.studio hash=$2b$12$XxVYp...(bcrypt)
user count: 2 | workspaces: 2 | generations: 17 | assets: 5
```

`lsof` confirms `TCP *:27017 (LISTEN)` and `TCP *:8001 (LISTEN)` — all interfaces. The macOS application firewall is **disabled** (`State = 0`) and the host holds a LAN address (`10.0.0.201`). Chroma answers unauthenticated on `/api/v2/heartbeat`.

**Compounding:** `chromadb==1.5.9` is affected by **GHSA-f4j7-r4q5-qw2c — pre-authentication code injection (Critical)**. The advisory's affected range is `>=1.0.0, last_affected 1.5.9`, and **1.5.9 is the latest release on PyPI — there is no fixed version to upgrade to.**

**Impact.** Any device on the same network reads and writes the entire database — user records, bcrypt hashes, every workspace and generation — and gets arbitrary code execution in the Chroma container. On a café or coworking network this is a full compromise of the dev machine's data.

**Recommendation (S — 2 minutes).** Bind both to loopback: `"127.0.0.1:27017:27017"` and `"127.0.0.1:8001:8000"`. Add Mongo root credentials for prod parity. Until Chroma is patched upstream, loopback binding is the *only* mitigation available for the RCE. Local dev infrastructure has no reason to listen on `0.0.0.0`.

### SEC-02 · High · Unauthenticated token issuance + unbounded paid-LLM abuse
`server/app/routes/auth.py:42-51`; `generate.py:44,111,196`; `documents.py:49`; `workspaces.py:132`; `templates.py:123,148`

`POST /api/auth/demo-login` issues a full 60-minute bearer token **with no credentials** — by design, for "Explore as demo." `require_not_demo` correctly blocks workspace *mutations*, but every generation route is deliberately exempt (a documented product decision: demo users must be able to generate). There is **no rate limiting anywhere in the application** (grep-confirmed: no slowapi, no limiter, no throttling middleware).

**Impact.** One anonymous POST, then loop `/generate/text` forever. Unbounded Anthropic + OpenAI spend (financial DoS) against your API keys. Each call also persists a Mongo document (`generate.py:87`), so it doubles as an unauthenticated unbounded write primitive.

**Recommendation (M).** Per-IP and per-user rate limits on `demo-login` and all `/generate/*`; a daily generation quota for `is_demo`. This is the single highest-value security control missing from the app.

### SEC-03 · High · Jinja2 loop-bomb freezes the uvicorn worker
`server/app/routes/templates.py:218` (and `:71`)

Uploaded `.docx` files are rendered as Jinja2 **template source** via docxtpl. `template_service.safe_range` caps a single `range()` at 100,000 — but **does not cap nesting**. `{% for i in range(100000) %}{% for j in range(100000) %}` is 10^10 iterations; the PoC was still spinning after 30 seconds.

The render call is **synchronous inside an `async def`, with no `to_thread` and no timeout** — so one request blocks the event loop and freezes the server for every other user. `discover_placeholders` (`:71`) has the same defect.

Note the codebase already knows the right pattern: `templates.py:180` and `ingestion_service.py:82` correctly use `asyncio.to_thread(...)` + `wait_for(30)`. These two paths were simply missed.

**Recommendation (M).** Wrap both in `to_thread` + `wait_for`. Better, per SEC-10: reject templates containing `{%` outright — only `{{var}}` substitution is a product requirement, which removes the entire Jinja *statement* surface and fixes this finding and SEC-10 together.

### SEC-04 · High · Zip-bomb — only the compressed size is capped
`server/app/routes/templates.py:65,171`; `assets.py:73`; `content_extraction.py:45,69`

`.docx`/`.pptx` are ZIP containers. Every size check is `len(data)` on the **compressed** upload; `DocxTemplate(BytesIO(data))`, `Presentation(...)`, and `Document(...)` then decompress into memory with **no uncompressed-size guard anywhere**.

Measured: a crafted 48 KB `.docx` yields a 50 MB `document.xml` — **1,011× amplification**. At the 10 MB upload cap that is roughly **11 GB of RAM** → OOM kill.

**Recommendation (S).** Before handing bytes to python-docx/pptx, open with `zipfile.ZipFile` and reject when `sum(zi.file_size for zi in infolist())` exceeds a bound (~100 MB) or the compression ratio exceeds ~100×.

### SEC-06 · High · Default JWT secret with no fail-fast, and the Dockerfile forces production
`server/app/config.py:18`; `Dockerfile:20`

`jwt_secret_key: str = "CHANGE-THIS-IN-PRODUCTION"`, and **nothing validates it at startup**. `Dockerfile:20` hard-sets `ENV ENVIRONMENT=production`, so a container launched without `JWT_SECRET_KEY` boots happily and signs tokens with a publicly-known key → anyone forges `{"user_id": "<any oid>"}` and becomes any user. Total auth bypass, gated only on one missed env var.

The local `server/.env` also uses a 33-char `change…` placeholder, so the failure mode is untested even in dev. `demo_password` and `demo_email` are likewise hardcoded defaults in source.

**Recommendation (S).** A Pydantic validator that **raises at startup** when `environment == "production"` and the secret is the default or shorter than 32 bytes. Fail closed, don't warn.

### SEC-07 · Medium · Raw exception strings streamed to the client
`server/app/routes/generate.py:101,186,274`; `documents.py:151`; `ingestion_service.py:119`

`except Exception as exc: yield _frame({"error": str(exc)})`. Reachable exception text includes **absolute server filesystem paths** (`FileNotFoundError` from storage), the storage-traversal guard's message (which echoes the rejected key), and Anthropic/OpenAI/Mongo/Chroma connection errors carrying **internal hostnames and ports**. The same string is persisted to the DB and served back via the asset API.

No path was found where an **API key** lands in exception text — the SDKs redact. So this is infrastructure disclosure, not credential disclosure.

**Recommendation (S).** Emit `{"error": "Generation failed."}` plus a correlation ID; `logger.exception` the detail server-side. ARCH-02's shared `guarded_stream` makes this a one-line fix in one place instead of four.

### SEC-08 · Medium · Prompt injection — the `<brand_context>` fence is not escaped
`server/app/prompts/text_post.py:56-58`; `image_card.py:78-80`

Retrieved chunk text is interpolated into the prompt **verbatim**, so an uploaded document containing `</source></brand_context>` breaks out of the fence and everything after it reads to the model as top-level instruction. Separately, `source` is the **raw filename** — `asset_service.py:34` stores `filename` unsanitized (`safe_filename` is applied only to the storage *key*), so a file named `x" kind="voice"><override>…` injects prompt attributes.

**Genuinely mitigating, and worth crediting:** an explicit `SECURITY:` clause in every system prompt; and structure is **never parsed from the token stream** — it comes from a forced `tool_choice` call with `strict: True` schemas and is re-clamped server-side. So a successful injection can *steer copy* but cannot smuggle new fields or reach code. Exfiltration risk is low: the context contains only that workspace's own documents.

**Recommendation (S).** Escape `<`/`>` in chunk text and filenames before interpolation; run `safe_filename()` on the stored `filename` too.

### SEC-09 · Medium · Login timing oracle (bcrypt skipped for unknown users)
`server/app/services/auth_service.py:37`

`if not doc or not verify_password(...)` short-circuits: when the user doesn't exist, **bcrypt never runs**. Measured on this machine: **known email ≈ 229 ms, unknown email ≈ 0 ms.** The error *message* is correctly uniform, but the timing delta is a trivial enumeration oracle — and with no rate limiting (SEC-02) it also enables unthrottled password spraying against a confirmed-valid account.

**Recommendation (S).** Always run a dummy `verify_password` against a static hash when the user is absent.

### SEC-10 · Medium (latent) · Untrusted templates reach Jinja; only the sandbox stands between them and RCE
`server/app/services/template_service.py:77-84`

User-uploaded file content **does** reach Jinja as template *source* (proven in SEC-03). Six standard sandbox-escape payloads were tested against this exact code path — `{{ ''.__class__ }}`, `{{ self.__init__.__globals__ }}`, `{{ cycler.__init__.__globals__.os }}`, `{{ lipsum.__globals__ }}`, and two others — and **all were blocked**. `SandboxedEnvironment` was the right call and it is holding.

**No RCE is being claimed.** The finding is that the sandbox is the *single* control between an uploaded file and code execution, with no defense in depth behind it. Any future Jinja sandbox-escape CVE turns this into instant RCE.

**Recommendation (S).** Pre-reject templates whose XML contains `{%`. Only `{{var}}` substitution is a product requirement — this eliminates the Jinja statement surface entirely and fixes SEC-03 at the same time.

### SEC-11 · Medium · CSS injection via unsanitized `@font-face` family name
`client/src/styles/brandFonts.ts:157-162`; `server/app/routes/workspaces.py:320`; `brand_extract_service.py:74-76`

The font `family` string is a **free-text user label** (not parsed from the TTF). It reaches a live CSS sink with **zero escaping on any hop**: the server applies only `.strip()[:80]`, and the client interpolates it straight into `style.textContent` as `font-family:"${family}"`.

**Proven.** Executed through the repo's own jsdom, the payload `X";}body{background:url("https://evil.tld/leak")}@font-face{font-family:"Y` produces a real, applied, document-wide CSS rule in the CSSOM.

**Honest impact assessment — this is not XSS.** Because the string is assigned via `textContent`, the HTML parser is never invoked; a `</style><img onerror=…>` payload was tested and produced **zero** element nodes. The JWT lives in localStorage, which CSS cannot read. What an attacker *does* get: outbound beacon requests on page load, full app defacement, and UI redress (overlaying a fake credential prompt). And workspaces are strictly single-owner (grep for member/share/invite/team → zero hits), so the direct path is self-inflicted. The one cross-actor path is the AI brand-extract flow, where `fonts.heading` comes from **LLM tool output with no length cap at all** — a prompt-injected brand image could emit a malicious family string that the user then accepts.

A real sanitization gap worth fixing now; not a breach.

**Recommendation (S).** Allowlist-validate at the server boundary (`^[A-Za-z0-9 _-]{1,80}$`), and on the client replace string interpolation with the CSSOM API (`new FontFace(family, src)` + `document.fonts.add()`), which quotes the family for you. Note the irony worth internalizing: the family name **is** already treated as hostile on the filesystem path (`brand_fonts.py:52-56` confines it against traversal) but not on the CSS path.

### SEC-12 · Low · Non-cancellable parse threads accumulate under repeated bomb uploads
`server/app/services/ingestion_service.py:82-88`; `templates.py:180-187`

The `to_thread` + `wait_for(30)` pattern correctly protects the event loop — credit where due. But `asyncio.to_thread` is **not cancellable**: on timeout the coroutine returns while the worker thread keeps running. PoC: after `wait_for` raised at t=1s, the thread kept spinning, advancing its counter **41 million times** over the next 3 seconds. Repeated bomb uploads accumulate live threads that nothing can reap.

**Recommendation (M).** Parse in a `ProcessPoolExecutor` (killable), or apply resource caps inside the parser.

### SEC-13 · Low · Demo user can mutate seeded generations
`server/app/routes/generations.py:54-63`

`PATCH /generations/{id}` is the one mutating endpoint without `require_not_demo`, justified as "these are the user's own generations, not the protected seed corpus." But the demo user's only workspace **is** the seeded corpus, so a visitor can overwrite `fields`/`image`/`accent_hex` on seeded demo generations — contradicting the stated intent of DECISIONS #15. Damage is bounded (re-seed fixes it) and the accent is palette-validated.

**Recommendation (S).** Confirm intent; if unintended, add `require_not_demo`.

### SEC-14 · Low · Middleware and header hardening gaps
`server/app/main.py:44-50,85-90`; `client/index.html`

- CORS uses `allow_credentials=True` with wildcard methods/headers — **but `allow_origins` is an explicit list, never `*`**, and auth is a `Bearer` header rather than a cookie. **Not exploitable as written**; the wildcards are untidy, not dangerous.
- **No global exception handler exists**, so FastAPI's default returns a bare 500 with no traceback. (The leak is the SSE path, SEC-07 — not here.)
- **No Content-Security-Policy** anywhere (no header, no meta tag). A CSP would have neutralized the exfil half of SEC-11 outright. Also no `frame-ancestors` → no clickjacking protection.
- Missing `TrustedHostMiddleware`, HSTS, `X-Content-Type-Options`, and an ASGI-layer body-size limit (every route reads the full body into RAM before checking `len(data)`).
- `main.py:88`'s SPA catch-all returns `index.html` with **200** for any unmatched path, including unknown `/api/*` — masking 404s.

### SEC-15 · Low · `_truncate()` measures bytes but slices characters
`server/app/utils/security.py:13-17`

The guard checks `len(password.encode("utf-8")) > 72` and then returns `password[:72]` — a **character** slice. PoC: 30 emoji = 120 bytes → branch fires → returns 30 chars = still 120 bytes. The helper does not do what it says.

**Not exploitable, and it introduces no collision class.** bcrypt truncates to 72 bytes internally regardless, and hash/verify apply the same helper, so they stay symmetric. The residual collision is bcrypt's inherent, well-known 72-byte limit — not something this code creates.

**Recommendation (S).** Delete the helper (passlib handles this), or fix to `password.encode()[:72]` and reject over-long passwords explicitly.

### SEC-16 · Low · `BrandColor.hex` is unvalidated server-side while `CardPreset.accent_hex` is
`server/app/models/common.py:20-24` vs `:81-86`. The client filters with a regex before submit, but a direct API call could store a junk hex. No current impact (`hexToRgba` sanitizes numerically and every other consumer is a CSS *property*, not a rule). Defense-in-depth inconsistency only — reuse the existing `_HEX_RE` validator.

## Build, tests, and tooling

### BUILD-01 · High · `npm run build` is broken on `dev`
`client/src/types/index.ts:57-60`; 7 construction sites

`BrandProfile` gained four required fields (`exemplars`, `brand_images`, `uploaded_fonts`, `card_presets`) as the exemplars/brand-images/fonts/card-presets features landed. Seven sites still build the old five-field shape. `npm run build` exits **2** with **9 TypeScript errors** (7 × TS2739 on `BrandProfile`, 2 × TS2345 on `ReadableStreamDefaultReader` mocks in `sse.test.ts`).

**Why the tests didn't catch it:** `tsconfig.app.json` includes `src`, so `tsc -b` type-checks the test files — but **Vitest transpiles via esbuild and never type-checks**. `vitest run` is green while `tsc -b` is red. The 20 test files are not a gate on types.

**Is it a runtime bug? No — a type gap only.** `buildBrandProfile` (`client/src/features/settings/brandIdentity.ts:73`) genuinely omits the four keys at runtime, but the server explicitly re-hydrates them (`workspace_service.py:104-113` preserves `logo`, `exemplars`, `brand_images`, `uploaded_fonts`, `card_presets` from the existing doc), and this is regression-tested. **No data loss.**

**Impact.** `dev` is unreleasable, and a dev→main release/tag pass (v0.8.0) is the next milestone.

**Recommendation (S, ~30 min).** Fix the 9 errors; add a shared `makeBrandProfile()` test factory so the next added field breaks one file instead of seven; gate it in CI (CI-01) so it cannot recur.

### TEST-01 · Medium-High · The entire authentication path has zero test coverage
`server/tests/*`

No `test_auth*.py` exists. Every route test overrides the dependency (`app.dependency_overrides[get_current_user] = lambda: _user_a()`), so the **real** `get_current_user` never executes in the suite. Never exercised by any of the 153 tests:

- `routes/auth.py` — `/login`, `/demo-login`, `/me` (all 3 endpoints)
- `services/auth_service.py` — never imported by any test
- `utils/security.py` — token create/decode, password hash/verify, the bcrypt truncation
- `utils/dependencies.py:17-37` — the token→user path, including the inactive-user 403

Untested branches that matter: expired token, tampered signature, missing claim, deleted-user-with-valid-token, inactive user, wrong password.

**Do not over-report this:** *authorization* **is** well covered. `get_workspace_or_404` runs for real in `test_isolation.py` (owner A → owner B's data → 404 across four paths), and `require_not_demo` is covered. The gap is **authentication**, not tenancy.

**Recommendation (S, ~2 hrs).** Add `server/tests/test_auth.py`. This is the single highest-value test addition in the repo.

### TEST-02 · Medium · Frontend has no flow tests and no request mocking
`client/src/**/*.test.*`

20 files / 72 tests, but **no `@testing-library/react`, no `jest-dom`, no MSW**. Eleven files do render components, but by hand-rolling `createRoot` + `act` — closer to "does it mount without throwing" than "does the flow work." Network is stubbed ad hoc with `vi.fn()`, so there is **no contract fidelity** between client types and FastAPI responses — which is precisely how BUILD-01's `BrandProfile` drift went unnoticed.

Zero coverage for: login → token stored → attached to requests; 401 → redirect; generate → SSE → render → save as a flow; asset upload → ingestion polling; **workspace switch → cache invalidation**. That last one is the sneaky one — a missing TanStack query key on workspace change renders workspace A's generations under workspace B, a tenancy bug the server's excellent `test_isolation.py` cannot catch because the *server* is answering correctly.

**Recommendation (M, ~1 day).** Add testing-library + MSW with one handler set typed against `client/src/types` (this alone would have caught BUILD-01), plus three flow tests: login, 401-redirect, workspace-switch cache isolation.

### TEST-03 · Low · Preservation guard asserts only 2 of its 5 protected keys
`server/tests/test_brand_images.py:168-169`. The guard at `workspace_service.py:110` protects five keys; the regression test asserts only `brand_images` and `exemplars`. Since BUILD-01 proves the client omits all four on every identity save, this guard is the **only** thing preventing data loss — and 40% of it is unasserted. ### CI-01 · Medium · No CI exists at all

## Accessibility

### A11Y-01 · High · The SSE token stream is inside `aria-live="polite"` — floods screen readers on the core flow
`client/src/features/generate/GeneratePage.tsx:478`; `PostCaptionPanel.tsx:50`; `DocumentPreview.tsx:69`; `CardPreview.tsx:168`

All four generation hooks append per SSE frame with no batching (`onText: (delta) => setState(s => ({...s, text: s.text + delta}))`), and each token re-renders a text node **inside** a live region. React rewrites the whole text node, so the screen reader re-announces the **entire accumulated text on every token** — hundreds of queued, ever-lengthening announcements per generation. On a long document that is minutes of unstoppable speech.

`CardPreview.tsx:168` is worse: the live region wraps the *entire* preview container, including the `contentEditable` card — so every keystroke while editing re-announces the whole card.

**Impact.** A screen-reader user cannot use the generate flow. That is the app's primary interaction.

**Recommendation (S — delete 4 attributes, add one announcer).** Remove `aria-live` from the streaming containers; set `aria-busy="true"` while streaming and announce **once** on completion via a separate visually-hidden polite region ("Draft ready, 412 characters").

### A11Y-02 · High · Accent foreground is chosen by HSL lightness, not luminance — CTA labels can hit 1.07:1
`client/src/lib/colorTint.ts:64`

```ts
root.style.setProperty("--accent-foreground", hsl.l > 60 ? "214 12% 12%" : "0 0% 100%");
```

HSL lightness is not perceptual luminance. Pure yellow `#FFFF00` has **L = 50** → `50 > 60` is false → foreground is set to **white**. White on yellow = **1.07:1**. Same failure for `#00FF00` (1.37:1), `#00FFFF` (1.25:1), `#FF9900` (~2.2:1) — all L=50, all get white text. Users set this hex freely via the brand color picker, and there is **no contrast guard anywhere** in the file.

`--ring` is overridden with the same raw hex, so a pale brand color also makes the **global focus ring invisible** (a cream `#F4F1E9` ring ≈ 1.05:1 on white).

The seeded Verdure brand (`#1C3A2E`) is safe, which is exactly why this won't show up in demo — the failure is conditional, silent, and total.

**Recommendation (M, ~30 lines).** Compute WCAG relative luminance and pick the foreground that maximizes ratio; if neither black nor white reaches 4.5:1, step the accent until it does. Clamp `--ring` lightness so it always reads. Note `contrastInk` in `CardCustomizePanel.tsx:128-142` has half the math already — but uses the same wrong model (gamma-space average rather than linearized luminance), so fix both.

### A11Y-03 · Medium · Contrast failures in the token palette

| Where | Ratio | Needs |
|---|---|---|
| `button.tsx:20` — destructive hardcodes `text-white`; dark `--destructive` `#F87171` is a *foreground* color used as a *fill* | **2.77:1** (dark) | 4.5:1 |
| `input.tsx:12`, `textarea.tsx:12` — `placeholder:text-muted-foreground/60` | **2.31:1** light / 3.05:1 dark | 4.5:1 |
| `text-muted-foreground` on `bg-surface-variant` (the status/type pills, recurring) | **4.32:1** light | 4.5:1 |
| `CardPreview.tsx:223` — `text-accent` on `bg-surface` (the "Add an image" nudge) | **3.73:1** dark | 4.5:1 |

Fixes are all S: add a `--destructive-foreground` token (none exists); drop the `/60` on placeholders (plain `text-muted-foreground` passes at 4.81:1); darken light `--muted-foreground` from `#6C737A` to ~`#5F666D` (one token change fixes the pills *and* gives body text headroom, currently a bare 4.56:1); use `--accent-strong` for accent-as-text in dark.

**Verified passing, for the record:** accent `#C2185B` on white is **5.87:1** (DESIGN.md's own 4.6:1 claim is conservative); success 5.02/8.94, warning 5.02/7.25, light destructive + white 6.57:1.

### A11Y-04 · Medium · Five ARIA radiogroups have no arrow-key navigation
`SettingsPage.tsx:59-85` (theme), `TemplatePicker.tsx:26-51` (used in 3 places), `CardCustomizePanel.tsx:73-103`, `CardPresetsSection.tsx:71-113`

Each is `role="radiogroup"` + `role="radio"` + `aria-checked` on real `<button>`s, with **no `tabIndex` management and no `onKeyDown` anywhere**. So all radios are individually tabbable (should be one stop) and **arrow keys do nothing** — but the ARIA contract says a radiogroup is arrow-navigated, so NVDA/JAWS in forms mode will trap on the group.

Not a blocker — they're real buttons, so Enter/Space works and the flow is completable. Hence Medium.

**Recommendation (M).** Cheapest and best: drop the custom roles and use Radix `RadioGroup` (already in the dependency family) or native `<input type="radio">` with styled labels — that gets roving focus, arrow keys, and grouping for free.

### A11Y-05 · Medium · Field validation errors are neither announced nor associated
`BrandIdentityEditor.tsx:358-360,371-372,431-433`. Error text renders in a bare `<span>` with no `role="alert"`, no `aria-invalid` on the input, no `aria-describedby`. **`grep -rn "aria-invalid" client/src` returns zero hits app-wide.** A screen-reader user submitting an invalid hex hears nothing. Contradicts DESIGN.md §4 and §6. (Form-level/async errors *do* use `role="alert"` correctly — the gap is specifically field-level validation.)

### A11Y-06 · Low · Assorted
- **No skip-to-content link** (`AppShell.tsx:14` has `<main>` but no `id`); with a persistent SideNav, keyboard users tab ~8 nav items on every page. DESIGN.md requires one.

### STYLE-01 · Low · The type scale from DESIGN.md was never encoded in Tailwind
`client/tailwind.config.ts` has no `fontSize` or `letterSpacing` extension, so components reach for arbitrary values: `text-[9px]`, `text-[10px]`, `text-[11px]`, `text-[15px]` across ~40 sites, and **six different eyebrow trackings** (`0.1em`, `0.12em`, `0.14em`, `0.16em`, `0.18em`, `0.2em`, `0.22em`) for what DESIGN.md §2 defines as *one* value. `SettingsPage.tsx:46` uses `0.2em`, `CardPresetsSection.tsx:50` uses `0.16em`, `HistoryPage.tsx:222` uses `0.12em` — same visual role, three values.

### STYLE-02 · Low · Google Fonts `@import` is the worst-case font load, and DESIGN's preload was never implemented
`client/src/index.css:1`. ## Architecture

No High findings. The layering is sound — zero service→route imports, and exactly one route→route import (ARCH-05). The debt is horizontal repetition of cross-cutting scaffolding.

### ARCH-01 · Medium · The upload validate/store pipeline is copy-pasted across 9 sites
`workspaces.py:87,146,174,240,325`; `images.py:89`; `assets.py:67`; `templates.py:60,162`

The `read → empty-check(400) → size-cap(413)` triad appears **9 times**; the full `read → validate → safe_filename → build_key → save` pipeline appears **7 times** — with **five different type-validation styles** across them (two shared resolvers, two inline extension checks, and one call whose return value is discarded).

**Why it matters:** this is the app's entire untrusted-input boundary, implemented nine independent times. It is also where SEC-04's missing zip-bomb guard has to go — and right now that means patching nine places and missing one. Divergence has already started (`add_font` validates inline rather than through a resolver).

**Recommendation (M).** A single `upload_service.py` with a frozen `UploadPolicy` per file class and one `read_upload()` gate. Nine sites → one. **Centralizing this centralizes the security posture** — which is exactly why it's the highest-value backend refactor.

### ARCH-02 · Medium · SSE scaffolding duplicated across `generate.py` and `documents.py`
`_SSE_HEADERS` and `_frame()` are **byte-identical** between the two files, and roughly **35 of the ~45 non-domain lines** in each of the four `event_stream()` bodies are identical — including the empty-corpus 409, the retrieval-failure frame, the `except: yield {error}`, and the `finally: yield [DONE]`.

That `finally` is ARCHITECTURE.md gotcha #3 ("always emit a terminal frame so the client unsticks on error") — an invariant currently enforced by **four independent hand-maintained copies**. The fifth generate route (and there will be one — this app adds a generation type per phase) that forgets it produces a client that spins forever.

**Recommendation (M).** `utils/sse.py` with `guarded_stream()`, plus a `require_ready_corpus` dependency and a `build_brand_context()` helper. Also makes SEC-07's fix a one-liner. Note the **frontend already solved this** (`lib/sse.ts` factors it correctly) — use it as the template.

### ARCH-03 · Medium · `docs/DATA_MODEL.md` and `docs/ARCHITECTURE.md` have drifted substantially
- **DATA_MODEL.md:** says four collections (there are **five** — `templates` is undocumented); `brand_profile` is missing all four newer sub-collections; `generations.type` is documented as `text|card` (actually `text|card|document|post_pack`); the `document` and `post_pack` output shapes are entirely absent; card `output` is missing `accent_hex`. **And it documents `png_export_key`, a field that does not exist anywhere in the codebase** — worse than a gap, because someone will write code that reads it.
- **ARCHITECTURE.md:** §2's repo tree omits 2 routes, 6 services, and 5 prompt modules, and lists a `client/src/pages/LandingPage.tsx` that **does not exist**. §6's API table describes roughly **half** the endpoints the app actually serves.

**Why it matters:** these are the files a new dev or an agent reads *before* touching a route or writing a migration. §7 (risks/gotchas) is still accurate and genuinely valuable — which is exactly what makes the stale sections dangerous: the doc reads as trustworthy.

**Recommendation (S).** Regenerate §2 from the tree and §6 from the OpenAPI schema so it can't drift again. **Leave §3/§4/§5/§7 alone — they're accurate and carry the design reasoning.**

### ARCH-04 · Medium · The generation-hook fork has already produced a live user-visible bug
`client/src/features/generate/useCardGeneration.ts` vs `usePostPackGeneration.ts`

These are ~85% structurally identical, with **~57 lines byte-identical** (`selectUnsplash`, `selectUpload`, the image-persist effect, `stop`, the workspace-reset effect). They are not different domains — they are the same domain with a different endpoint and a different output nesting.

**And the drift has already happened:** `usePostPackGeneration` has **no `clearImage`**. A user in LinkedIn-post mode who picks an image **cannot un-pick it**, while the same user in card mode can. That is a real capability gap in shipped code, caused directly by the fork.

**Recommendation (M).** Extract `useStreamedGeneration` (the abort/status/reset state machine, shared by all four hooks) and `useCardImageSelection` (shared by these two) — which **fixes the missing `clearImage` for free**. The four hooks survive as thin domain-specific compositions. Highest-value frontend refactor.

### ARCH-05 · Low · Assorted backend structure
- **Nine hard caps live in six different modules**, split across the route and service layers with no principle distinguishing them (`MAX_EXEMPLARS` in a service, `MAX_UPLOADED_FONTS` in a route, both enforced in routes). "What are our DoS caps?" currently requires reading six files. → one `app/limits.py` (S).
- **The only route→route import in the codebase** (`workspaces.py:21` imports from `routes/images.py`) — an isolated layering leak, and the seed of ARCH-01. Dissolved for free by ARCH-01 + the limits module.
- **`generation_service.py` vs `generations_service.py`** — the Anthropic client vs the Mongo persistence layer, two unrelated concerns whose names differ by one character, both imported into the same files. Rename the former to `ai_service.py` — which also matches what ARCHITECTURE.md already calls it (S).
- **Cap-and-dedupe checks live in route handlers** while the service `$push`es unconditionally → a TOCTOU (two concurrent uploads both see `len == MAX-1`) and an invariant that no other caller can honor. Push the caps into the service writes, ideally as conditional Mongo updates (M).

### ARCH-06 · Low · Oversized files — verdicts differ, and two should be left alone
- **`GeneratePage.tsx` (525)** — **split.** It's six components in a trenchcoat (four independent Modes + PostOutput + EmptyCorpus) sharing nothing but a grid shell. `GeneratePage` becomes ~70 lines of mode-routing. Clearest split in the codebase (S).
- **`BrandIdentityEditor.tsx` (561)** — **partly.** The 370-line form is the problem; hoist `LogoPreview`/`FontPreview` and break the five fieldsets out (S).
- **`HistoryPage.tsx` (487)** — **mostly fine**, cohesive. Split out `HistoryCard`/`DetailDialog` (S), but do *not* unify their two three-way branches: one renders a grid tile, the other a modal body.
- **`cardElement.tsx` (527)** — **leave the abstraction alone.** The three archetypes look 60% duplicated and it is tempting to unify them. Don't. They are locked visual layouts in Satori's CSS subset, and the file's entire contract is "preview == export by construction." A shared abstract layout would leak the moment one archetype needs a property Satori handles differently — producing exactly the preview/export mismatch this file exists to prevent. The pieces that *should* be shared already are. Mechanical file-split only.

### Things that look like debt and are actually fine
Called out deliberately, because each is a plausible target for a well-meaning refactor that would make the code **worse**:
1. **`client/src/lib/sse.ts`** — the four `stream*` wrappers are 8-line typed URL bindings over a correctly-factored core. This is the right design; it's the *template* for ARCH-02, not a target.
2. **`storage_service.py`'s five `build_*_key()` one-liners** — the explicit per-namespace function **is** the mechanism that makes "keys are always server-derived" auditable. A generic `build_key(kind, …)` makes that security property *harder* to verify.
3. **`document_service.py` (341)** — flagged in my brief as the critical unknown. It is **clean**: no Jinja, no template source, XML-escaped PDF strings. The "repetition" is three incompatible library APIs (python-docx / reportlab / python-pptx), deliberately kept explicit so the formats agree by construction.
4. **`rag/qdrant_store.py`** — not dead code; it's the documented prod backend, and its existence is what proves the `VectorStore` protocol actually abstracts.

## Deployment `[deferred-deploy]`

Deployment is deferred per `docs/PLAN.md`, so these are weighted down — **except DEP-01**, which is a risk today.

### DEP-01 · High `[today-risk]` · No `.dockerignore`: live API keys would be baked into image layers
`Dockerfile:17`

There is no `.dockerignore` anywhere. `server/.env` exists on disk (untracked, correctly gitignored) and holds **live-shaped Anthropic (108-char), OpenAI (164-char), and Unsplash (43-char) keys**. **`.gitignore` has zero effect on the Docker build context.** `COPY server/ ./` with the repo root as context would sweep in `.env`, `server/.venv/` (674 MB), `server/storage/` (20 user-uploaded files), and every cache directory.

Image layers are immutable and content-addressed — `docker history` / `docker save` / a registry pull recovers `.env` verbatim, and deleting it in a later `RUN` would **not** remove it from the earlier layer.

**Why High and not Critical:** the exposure is latent. Nothing publishes this image, and the build currently **fails at `Dockerfile:18`** (DEP-02) before producing a final image — an accidental safety net. But layer 17 materializes into the local build cache the moment anyone runs `docker build`, and DEP-02 is a one-line fix away from removing that net.

**Recommendation (S).** Add `.dockerignore` (`**/.env*` with `!**/.env.example`, `**/.venv/`, `**/node_modules/`, `server/storage/`, caches, `.git/`). Inject secrets at runtime, never `COPY`. **Rotate the three keys if `docker build` has ever run on a shared machine.**

### DEP-02 · Medium · The Dockerfile cannot build (two independent breakages)
`Dockerfile:4,8,18`. Stage 1 sets `WORKDIR /app/client` and `vite.config.ts` has no `outDir` override, so artifacts land at **`/app/client/dist`** — but stage 2 does `COPY --from=frontend-builder /app/dist ./dist`. That path does not exist. (Proven statically; no `docker build` was run — deliberately, since that would materialize DEP-01's secret layer.)

Stacked on top: `Dockerfile:8` runs `tsc -b`, so **stage 1 would already fail on BUILD-01's 9 type errors** before ever reaching line 18.

The `main.py` side is correct — it mounts `dist` relative to `/app`, so only the COPY *source* is wrong. One-line fix.

### DEP-03 · Low `[deferred-deploy]` · Dockerfile hardening
Runs as **root** (no `USER`); `gcc` installed for wheel builds and never removed (image bloat + a compiler for an attacker); no `HEALTHCHECK` despite a working `/api/health`; base images pinned to floating tags (`node:20-alpine`, `python:3.12-slim`), so builds aren't reproducible; dev tooling (ruff/mypy/pytest) ships into the production image via `requirements.txt` (TOOL-04).

### Git history is clean (good news, and it bounds DEP-01)
```
git log --all --diff-filter=A --name-only -- '*.env' '*.pem' '*.key'  → empty
git log --all -S'sk-ant' --oneline                                     → empty
git log --all -S'sk-proj' --oneline                                    → empty
```
**No secret has ever been committed on any branch.** `.gitignore` has done its job from the start, and `server/storage/` is untracked. The secrets in DEP-01 are exposed to a *hypothetical Docker build*, not to anyone with repo access. **No history rewrite is needed.**

### Verification method
Every Critical/High finding was verified by execution, not inference: the Mongo/Chroma exposure by connecting over the network and reading records; the build failure by exit code; the zip bomb, loop bomb, Jinja sandbox escapes, and login timing oracle by in-memory PoC; the CSS injection by parsing the resulting CSSOM in the repo's own jsdom; the dependency CVEs by OSV lookup with advisory IDs. The Dockerfile bug was proven **statically and deliberately not by building** — a build would have materialized the secret-bearing layer described in DEP-01.

### Coverage-gap matrix (backend)

**Zero direct coverage:** `routes/auth.py` (all 3 endpoints), `services/auth_service.py` (never imported by any test), `utils/security.py` (JWT + password hashing), `utils/dependencies.get_current_user` (always overridden), `routes/health.py`, `rag/embeddings.py` + `chroma_store.py` (all tests use `FakeVectorStore`, so no real backend is ever exercised). `services/asset_service.py` has no direct tests.

**Correction to the initial exploration:** `storage_service` and `workspace_service` were reported as untested — **they are not**. Both are directly imported by multiple test files and heavily exercised through route tests. The real service-layer holes are `auth_service` and `asset_service`.

**Ranked by risk:** (1) the entire authentication path — by a wide margin; (2) client-side auth + workspace-cache isolation (a stale TanStack cache can cross-render tenants even when the server answers correctly); (3) `asset_service`; (4) real vector-store backends; (5) `generations_service` (pagination only); (6) `health` — trivial, and should not be allowed to crowd out #1.
